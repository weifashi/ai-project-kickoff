# 项目启动到交付：阶段、产物与放行

本参考是工作流程，不是“所有行业都已覆盖”的认证清单。
先按 [平台裁剪](platforms.md) 分开记录平台、三档深度与交付目标；默认标准，风险叠加取最高档。
默认产物位置、命名和维护规则以 `documentation-and-operations.md` 为唯一来源；本文只指向所需内容。
已有可信产物和明确确认直接采用，记录版本与适用边界；不为了走流程让用户重复批准。

## 一、先分开记录三件事

### 1. 决策事实

- `采用`：用户已明确选择，或任务已授权在清楚边界内执行；注明依据。
- `只建议`：AI 提供的选项，尚不能当作用户业务规则或审批结论。
- `未验证`：待调研、待测试或缺少环境；列负责人、补证方式和影响。
- 用户说“快一点”不能转写为“允许猜测业务、跳过安全限制、已批准上线”。
- 只问会改变范围、风险或实施路径的关键问题；能读代码和查资料的事实先查。

### 2. 产物状态

| 状态 | 含义 | 必要记录 |
| --- | --- | --- |
| `draft` | 方案草案，可讨论，不代表允许实施 | 假设、待决项 |
| `approved` | 对应版本已由有权者明确确认 | 谁、何时、确认范围及依据 |
| `implemented` | 内容已对应到实际实现 | 实现版本、偏差和证据 |
| `superseded` | 被新版本替代，保留追溯 | 替代版本及原因 |

产物 `approved` 不等于测试通过；产物 `implemented` 不等于已部署或运行正常。
不凭 AI 自审、时间压力、沉默或其他代理口述伪造批准。

### 3. 共同质量门

G0–G6 的定义与状态语义只维护在 [主入口的放行门](../SKILL.md#放行门按本次目标使用)。
本篇各阶段仅列具体动作、产物和证据，不另定义第二套门。
门状态为 `pass / na / unverified / blocked`，与产物状态分开；`approved` 不是测试通过，`pass` 不是用户批准。
受阻时可继续独立的只读调查或草案，不能把依赖该门的工作宣称通过。
只交付方案时，按目标说明 G4–G6 的不适用范围；不把未执行的实现/安装记为通过。
阶段可短、产物可合并；合并不是删除证据或偷换验收标准。

## 二、S0：定位上下文与授权 → G0

**输入**：当前请求、路径、团队约定、已有成果与可用工具。
**动作**：
1. 确认新项目/已有项目，读取任务路径上的规则；已有仓库查分支、改动、运行入口。
2. 识别目标用户、交付平台、关键外部系统、负责人、时间/预算/语言等硬约束。
3. 分开列读写、运行测试、联网/费用、提交、发布、迁移、数据操作等授权边界。
4. 分开记录主平台、轻量/标准/高风险档位、交付目标；按 [平台裁剪](platforms.md) 定档，不因只做草案或赶工降低风险档位。
5. 对未知工具/API 先做必要的只读或低风险探索，不因工具名相似假定可用。
**产物**：启动摘要、事实/假设/待决清单、授权矩阵、裁剪记录。
**放行**：工作对象与可执行边界明确；缺失的生产授权不能由本地开发授权替代。
**压缩方式**：小任务一段摘要即可；仍保留环境与副作用边界。

## 三、S1：问题发现、头脑风暴与调研 → G1

**输入**：G0 结果、用户原始诉求、现有流程/反馈与业务事实。
**动作**：
1. 用“谁，在什么场景，想完成什么，现在被什么阻碍，损失是什么”写问题。
2. 区分用户目标与指定解决手段；检查不开发、调整流程、复用现成能力等方案。
3. 头脑风暴可分产品、工程、设计、运营等视角，但全部标为 AI 分析。
4. 有真实用户/客服/访谈材料时核对来源；没有时写“用户研究未验证”，不编访谈。
5. 查证会影响决策的兼容性、政策、第三方成本和限制；优先当前官方原始来源。
6. 对可行方案比较价值、风险、交付成本与退出成本，不做与决定无关的热度调查。
7. 收敛一个 MVP：必须做、暂不做、明确不做；多子系统拆批，保留依赖。
8. 将目标改写为可观察验收：“给定条件 → 执行操作 → 可见结果/失败反馈”。
9. 关键业务歧义请有权者裁决；不将 AI 角色投票视为真实用户需求确认。
**产物**：问题简报、调研与来源、方案取舍、MVP/非目标、验收与未验证假设；方案用 [html-mockup](../../html-mockup/SKILL.md) 阶段 A 讲清并留档。
**放行**：目标和边界可判断、必需决策明确，用户已确认的部分附依据直接沿用。
**压缩方式**：成熟需求可复用既有说明，只补变化；不强制每次重新做完整访谈。

## 四、S2：信息架构、任务流程与体验原型 → G2

**输入**：已确定的 MVP、角色/权限、核心任务、内容和验收场景。
**动作**：
1. 有 UI：列页面/入口、导航与信息层级，画核心任务路径，不先堆装饰组件。
2. 无 UI：列命令/端点/公共方法、输入输出、错误约定和成功/失败调用示例，并做契约/流程 HTML；不造虚假业务页面。
3. 覆盖本轮适用的加载、空、成功、错误、权限不足、取消、重试和恢复状态。
4. 用“页面/入口 → 用户操作/请求 → 业务结果 → 失败后的去向”讲清行为。
5. 权限和交易等高风险变化同时展示确认、执行中、结果不明与安全恢复路径。
6. 原型保真度只需支持本次决定；关键交互、真机能力或复杂数据流需更贴近实际。
7. 明确假数据、假交互、未接服务和未验证设备；不把原型演示说成生产能力。
8. 有视觉工作时沿用现有品牌/组件/平台习惯；无依据不强套审美或新增设计系统。
9. 收集有权者对关键规则的确认；已有确认记录仅核对是否仍适用。
**产物**：IA/流程、状态表、原型或契约、反馈与修订记录。
**放行**：关键任务能被理解和演练；影响业务的分歧已解决或在范围外明确隔离。
**压缩方式**：单命令工具可将几条调用示例与状态流放进一页 HTML；仍走 html-mockup，不强造登录页、数据库或后台。

## 五、S3：设计、架构与高风险 spike → G3

**输入**：体验/契约、非功能约束、团队能力、既有系统和风险列表。
**动作**：
1. 默认沿用可维护的团队技术栈；只有明确缺口才比较新技术和迁移成本。
2. 画系统边界与关键数据流；仅增加帮助决策的架构视图，不强制画全层级。
3. 列数据所有者、状态转换、持久化需要、访问边界和外部依赖；允许无数据库。
4. 明确适用的接口契约、版本兼容、超时/重试、幂等、并发和错误传播。
5. 将可用性、性能、容量、可访问性、安全和成本写成有场景的目标，避免空泛口号。
6. 把未知且可能推翻架构的事项排前面：第三方限制、设备能力、权限或数据迁移等。
7. 为每个必要 spike 写假设、最小实验、时间/费用边界、成功阈值与退出条件。
8. 用获准环境验证；合成/脱敏数据优先，真实服务费用和真实数据另按授权处理。
9. 记录成功、失败、替代路径及残留未知；spike 代码默认可丢弃，不自动升格生产。
10. 将验收映射到检查方式和环境；识别模拟覆盖不了的真设备/外部系统证据。
**产物**：架构概要、关键决策/替代方案、数据与接口约定、spike 证据、验证计划。
**放行**：关键可行性已有证据或已安全避开；未知项有明确边界，不能猜测为“支持”。
**压缩方式**：低风险改动可用一张边界图与数条决策；不默认微服务、消息队列或云服务。

## 六、S4：开发准备与最小真实垂直切片 → G4

**输入**：通过的必要前置门、实现计划、最终验收场景与授权环境。
**动作**：
1. 准备可复现的运行/检查入口、必要配置说明、依赖锁定及合成测试数据。
2. 核对仓库改动与隔离方式，保留用户已有工作；不覆盖不属于任务的文件。
3. 拆成可验收的垂直切片：入口 → 业务规则 → 必要依赖/存储 → 用户可见结果。
4. 不把“先写完所有页面、以后接数据”当成最小真实切片。
5. 先做最重要且有风险的闭环，覆盖一个关键失败/恢复路径，而不只演示 happy path。
6. 按项目要求补受影响测试和审查；没有测试框架时采用与风险匹配的可复现检查。
7. 显式区分模拟、沙箱和真实集成；模拟证明不了的能力保留未验证标记。
8. 多代理仅在已授权且任务可独立时分工，写清文件边界、共享契约和合并验证责任。
9. 实际结果与原方案不同时更新决策和验收；影响业务的变化不能静默替用户决定。
**产物**：可运行切片、对应源码/配置、自动或可复现检查、真实集成与失败证据。
**放行**：切片在指定环境从真实入口得到真实结果；只有静态页面/桩服务不能记通过。
**压缩方式**：纯本地 CLI 的“真实”可以是实际文件输入输出，不强制接远程服务。

## 七、S5：完整实现与最终制品验证 → G5

**输入**：已验证切片、剩余范围、风险/回归清单、计划交付形式。
**动作**：
1. 完成范围内切片并核对每条验收；删除或明确隔离未交付入口，避免“按钮看似可用”。
2. 审查业务规则、权限、数据变更、兼容性与异常路径，保持改动最小且可追溯。
3. 对最终代码重跑受影响检查；旧版本结果、仍在运行和截断输出均不能替代通过。
4. 在目标模式构建实际制品；按平台验证静态站、部署包、安装包、库包或可执行文件。
5. 区分源码检查、构建成功、制品启动、集成通过和真实业务验收，不以其一代替全部。
6. 若含迁移，验证兼容窗口、备份与恢复/前向修复方案；不得假设所有迁移可逆。
7. 核对分发内容不含密钥/个人数据，记录版本与哈希等适用的制品身份。
8. 测试环境、硬件、权限或外部账号缺失时列精确未验证项，不伪称全功能完成。
**产物**：最终制品、验收矩阵、审查/检查日志、已知限制及发布候选说明。
**放行**：所称“通过”都有最终版本证据；未验证项不得掩盖阻断交付的实际风险。
**压缩方式**：文档-only 不跑无关业务构建；库项目不强做 GUI 测试。

## 八、S6：发布、运营与交接 → G6

**输入**：最终制品、发布/安装授权、目标环境、恢复方案和责任人。
**动作**：
1. 发布前重新核对对象、环境、变更范围及授权；开发完成不自动授权部署或花费。
2. 制定适用的发布、备份、回滚/前向修复、监控与验收步骤；小工具可用轻量运行说明。
3. 在获准范围内执行，保留实际版本和操作结果；副作用结果不明先查状态再决定重试。
4. 验证目标中的制品身份、启动/健康与关键业务；“流水线绿灯”不是业务已正常。
5. 明确失败阈值、恢复负责人和通知路径；不擅自删除数据来“清理失败”。
6. 完成交接：如何运行、如何验证、关键规则、数据/表字段变化、已知限制和下一步。
7. 明确服务/内容/依赖的维护责任、必要告警、成本关注点和停止/退役方式。
8. 未获上线授权时交付候选制品和步骤，注明“未发布”；不能用文档代替实际发布证据。
**产物**：交付/发布记录、恢复与运行说明、AI 接手信息；有实际 diff 时按 html-mockup 阶段 B 出变更报告，否则只报方案/现状，不编造改动。
**放行**：在承诺范围内可接手、可验证、可恢复；“已交付”与“已上线运营”分开表述。
**压缩方式**：草案交付无需假造运维；离线应用无需强上在线监控，但要说明诊断办法。

## 九、持续变化与阶段回退

- 关键假设被推翻：回到对应阶段，不用继续堆实现证明已投入成本“没有白费”。
- 范围变更：更新 MVP/验收、受影响门和授权；保留旧版为 `superseded`。
- 新证据使旧检查失效：对应门退回 `unverified`，重跑受影响验证而非全流程重来。
- 交接只记录必要上下文、文件、版本和证据，不保存密钥、个人素材或无关会话全文。
- 赶工时删减范围、降低原型保真度、合并文档；资金、敏感数据、权限和不可逆风险不能因此降档，授权与证据不能删。
- 跨会话状态和双端同步引用 [状态索引](documentation-and-operations.md#13-最小状态索引) 与 [同步版本](sync-and-versioning.md)，不在聊天里另维护一套“最新”。
