# 原型、界面设计与评审归档

本篇是本技能内原型与界面设计的详细来源；资料总目录、运维与证据保管见 [文档与运维](documentation-and-operations.md)。
适用本技能全部项目：方案与报告必须经过 [html-mockup](../../html-mockup/SKILL.md)。有 UI 画页面；无 UI 画契约/流程 HTML，不强造登录、后台或数据库，也不能因无 UI 将 html-mockup 记为 `na`。
本文件属于技能草案，不代表已安装、已实施或已获得任何公开服务授权。

## 0. 必经工作流与唯一源码

- 阶段 A 讲方案：信息结构、主流程、失败/恢复、取舍与待决项；按档位控制篇幅与保真度，不省掉 HTML。
- 阶段 B 讲改动：**只有存在实际 diff** 时制作，逐项对应原规则 → 新规则 → 触发条件 → 业务/字段影响；无 diff 只交方案或现状说明，不编造“已改”。
- 读取仓库兄弟技能的当前版本，不安装、不改本机全局 skills。缺失时明确 `blocked` 及路径，不默默跳过或另写一套替代流程冒称已执行。
- 本项目已明确要求 Git 归档：项目内 `source/` 保存可编辑原件，`snapshots/` 与 `reviews/` 留证；临时 `preview_html`、8008 或 `~/www` 是展示副本，不是唯一源码。
- html-mockup 若沿用旧“孤本仅在展示目录”约定，以本项目明确的 Git 归档要求为准；只调整当前项目产物，不回写机器全局技能。默认目录只见 [资料地图](documentation-and-operations.md#2-默认资料地图)。
- 预览和外部公开是独立权限；内网工具可用不代表可上传内部页面。长期来源与双端同步见 [同步与版本](sync-and-versioning.md)。

## 1. 先确定要验证的问题

- 读取现有产品、需求、真实页面与组件；不要仅凭记忆重画当前系统。
- 写明需求 ID、目标用户、使用场景、用户任务、成功条件与不做范围。
- 新项目没有真实页面时，标成“拟议界面”，不能写成当前已上线页面。
- 从页面截图取证前确认授权；优先合成数据，不读取无关个人桌面或真实客户资料。
- 现有截图只证明截图时刻，不自动证明其业务规则仍与当前版本一致。
- 业务、技术或权限约束尚未查明时列为待确认，不能通过漂亮界面掩盖。
- 选择本轮要回答的问题：入口找不找得到、规则是否合理、流程是否完整，还是视觉是否一致。
- 为每个问题指定观察方式与通过条件；“看着不错”不是可复现的验收标准。

## 2. 原型之前的三个产物

不一定新增三份文件，可写在需求说明或原型 `index.md`，并保留链接。

### 2.1 信息架构 IA

- 列出主要页面、导航层级、入口、返回路径、跨页面依赖。
- 标记公开区、登录区、角色限定区，以及移动端与桌面端是否共用结构。
- 用用户理解的词命名页面；已有系统优先沿用真实业务用语。
- 记录对象之间的关系，例如“项目包含任务”，避免先画按钮再补业务对象。
- 原型需要的内容清单包括标题、标签、说明、错误提示和帮助入口。

```text
workspace
  +-- overview
  +-- projects
  |     +-- project-detail
  |           +-- tasks
  +-- settings
```

ASCII 对齐区域只用半角标识；中文解释写在图外，不靠空格对齐中文。

### 2.2 用户任务与流程

- 每个主要任务写“谁 → 从哪进入 → 做什么 → 何时算完成”。
- 覆盖起点、前置条件、主路径、可选路径、取消、返回与恢复。
- 标出收费、提交审批、发送通知、删除、授权等不可忽略的副作用。
- 显式写出系统边界：用户点击后，本系统处理到哪一步，外部系统接手到哪一步。
- 多角色接力时写清当前负责人、下一角色及待办到达方式。
- 将主任务关联需求 ID；不要用没有任务背景的页面堆叠代替流程。

### 2.3 状态矩阵

| 对象或页面 | 状态 | 用户能做什么 | 系统反馈 | 数据或权限影响 |
|---|---|---|---|---|
| 列表 | 无记录 | 新建、查看说明 | 有意义的空态 | 不伪造统计 |
| 列表 | 加载中 | 取消或等待 | 明确加载状态 | 不重复请求 |
| 编辑表单 | 校验失败 | 修正输入 | 字段错误与摘要 | 保留合法输入 |
| 提交动作 | 请求超时 | 查询状态后决定重试 | 结果尚不确定 | 不直接当作失败重发 |
| 详情 | 无权限 | 返回、申请权限 | 不泄露受限内容 | 按真实权限规则说明 |
| 外部服务 | 不可用 | 重试或替代路径 | 降级说明 | 不冒充已处理成功 |

- 按项目补充部分成功、并发修改、离线、过期、审核驳回等实际相关状态。
- 对“不适用”的状态给理由，不为了填表臆造业务行为。
- 状态变化写触发条件、允许角色和退出条件；原型演示的假数据不能充当实现承诺。

## 3. 选择保真度与交付形态

| 要回答的问题 | 优先方式 | 不应误解为 |
|---|---|---|
| 页面结构、主任务、入口是否合理 | 低保真线框、任务流与状态表 | 视觉定稿 |
| 文案、版式、层级、品牌一致性 | 高保真静态原型 | 真实业务可用 |
| 表单、切换、分步流程是否可理解 | 可交互代码原型 | 已接入真实后端 |
| 当前代码改动对用户有什么影响 | 真实页面对照与规则说明 | 新需求已获批准 |

- 默认用足以回答问题的最低成本 HTML；ASCII、线框与契约示例可嵌入说明页，高风险流程先验证交互再打磨视觉。
- 低保真通过不等于高保真或生产实现通过；在记录中分开写结果。
- 已有设计系统先复用；只在缺口确实存在时补 token、组件或模式。
- 新设计规则归档到 `docs/design/design-system/`，记录使用范围与维护人。
- 不为一次原型顺手替换产品技术栈、引入大型依赖或重做全套组件。

### 3.1 静态说明原型

- 用于讲清页面、规则、对照、状态流转和评审问题。
- HTML 优先自包含单文件；样式、脚本、必要图形内联，使用系统字体。
- 不依赖 CDN、远程字体或外链图片才能展示；导航链接与资源加载应分别检查。
- 页面内明确写“原型 / mock 数据 / 非生产系统”，并注明版本与需求 ID。
- 界面帧内只放拟议或真实界面文字，讲解标注放在帧外，避免被当成产品文案。
- 自包含不等于可随意分发：嵌入的图片、字体、截图仍受许可与隐私限制。

### 3.2 可交互代码原型

- 仅在需要真实点击、状态切换、组件评审时使用相应代码形态。
- 放入项目已有的原型或沙盒目录；在原型索引记录实际源码入口和启动方式。
- 使用隔离 mock 数据；不默认调用真实支付、邮件、短信或收费 API。
- 列出可点范围、未实现区域、硬编码响应和与真实产品的差异。
- 不把可交互原型悄悄并入生产路由、生产依赖或部署流水线。
- 若明确要求复用为生产代码，另行补架构、测试、安全和可维护性检查。

## 4. 把页面画出来，也把后果讲清楚

每个主要任务至少能回答以下链路，说明必须对应本轮原型版本。

```text
page -> action -> visible-result -> data-effect -> affected-role
```

- 页面：准确的页面名、入口、角色与当前状态；必要时带真实路由但不含凭证。
- 操作：点哪个按钮、输入什么、选择哪个筛选、确认什么，不写成抽象函数名。
- 可见结果：跳转、提示、列表更新、禁用、等待还是错误；前后状态要一致。
- 数据结果：保存什么、何时生效、是否发通知、影响其他哪些人。
- 无界面影响的改动写“用户无感知，仅……变化”，不要强行造页面。
- 改动报告需讲原规则 → 新规则 → 触发条件 → 影响对象，并链接源码或需求证据。
- 表字段、API、权限等引用其权威源码或文档；不要在原型里另造一套 schema。

示例说明：“任务详情 → 修改负责人并保存 → 显示新负责人 → 保存指派关系并通知接收人”。
若通知仅为建议，明确写“拟议通知，待业务确认”，不能描述为已实现事实。

## 5. 浏览器验证，不止检查 HTML 文本

- 对最终原型版本实际打开浏览器渲染；记录浏览器版本、视口与文件版本。
- 至少检查一个窄视口和一个宽视口；尺寸按目标设备确定，例如 390px 与 1440px。
- 测量文档和关键容器的横向溢出；宽表或宽图可局部滚动，不应意外撑破整页。
- 检查正文、按钮、提示与图中标签是否截断、遮挡、过密或颜色难辨。
- 需要横向滚动的内容给可见提示；不要把缩小到无法阅读当作修复。
- 可交互原型检查键盘进入顺序、焦点可见、表单标签、错误提示和主要操作反馈。
- 结合目标要求检查对比度、放大和非颜色提示；不能凭截图宣称符合全部 WCAG。
- 图表需实际渲染成图，不把流程图源码当完成图交付。
- 保存关键页面和状态的截图；截图文件名包含版本、页面、状态与视口。
- 修改布局、字号、数据或图表后，对最终版本重跑受影响渲染与溢出检查。
- 缺浏览器、渲染器或测量工具时写具体缺项，检查状态记 `unverified`。
- 静态解析通过、临时预览可打开或代理口头结论，都不能代替上述实际证据。
- 原型验证只证明原型；不能据此宣称生产功能、权限控制或数据库写入通过。

## 6. 用户反馈与批准记录

- 将评审问题写在页面外的说明区：要决定什么、备选方案、主要取舍。
- 提供可复现的评审任务，而不是只问“满意吗”；记录完成困难和歧义。
- 反馈记录包括日期、反馈人或角色、原话或可靠摘要、关联页面与版本。
- 区分观察事实、个人偏好、业务约束和待验证假设，不能把推断写成用户承诺。
- 每条意见记录处理结论：采纳、拒绝并说明原因、延期或待确认。
- 修改后说明解决了哪条反馈、还有什么未解决；必要时安排对应范围复审。
- 批准记录必须有真实批准人、日期、批准范围、原型版本和可追溯消息或工单。
- “已发送”“无人反对”“AI 自评通过”都不等于用户批准。
- 没有批准证据时保留 `draft`，或者写待批准；不能填造批准人或补写虚假日期。
- 涉及新增业务范围、费用或高风险副作用时，按主技能的授权边界另行确认。

## 7. 原型必须长期可找，不依赖聊天历史

默认目录只由 [资料地图](documentation-and-operations.md#2-默认资料地图) 定义。
已有项目沿用现有位置，在 `docs/index.md` 建映射；按实际产物建立，不制造空目录。
以下仅解释该地图中的产物角色：

- `index.md`：需求 ID、用途、负责人、版本、状态、源码入口、预览方式和批准证据索引。
- `source/`：HTML、线框、图形源码等可继续编辑的原件；代码原型在既有沙盒时放入口链接。
- `snapshots/`：关键状态截图、可分发导出件；大文件按证据保管规则放受控制品库并留索引。
- `reviews/`：评审问题、反馈、决议和复审记录；敏感原始材料放受控位置，只保留安全引用。
- 每个版本记录关联需求、变更摘要、作者、生成工具和相对于上一版的差异。
- 被替代的版本标 `superseded`，指出替代版本；不无声覆盖唯一批准记录。
- `implemented` 需关联实际实现版本和验收范围，不意味着原型中的所有设想都已落地。
- 资产清单记录图片、字体、图标及参考素材的来源、许可、修改和可分发限制。
- 自制或生成资产也标来源；不能把“网上找到”当作许可证明。
- 临时 `preview_html`、8008 链接或截图聊天消息只作展示入口，不是长期档案。
- 不为展示擅自开放公网端口、更改共享权限或上传内部页面；先确认现有授权和内容分级。
- 需要临时展示时指向已归档版本，记录链接有效期；服务失效后源码仍应可还原。
- 记录模板可参考 [原型记录](../assets/templates/prototype-record.md)；跨页面状态只引用 [最小状态索引](documentation-and-operations.md#13-最小状态索引)。

## 8. 状态与交付检查

- 文档生命周期统一用 `draft / approved / implemented / superseded`；状态与证据一起维护。
- 检查项使用 `pass / na / unverified / blocked`，不要混用文档生命周期状态。
- G0..G6 的阶段定义以主 `SKILL.md` 为准；本篇只提供相关设计和交付检查的证据。
- `pass` 要有实际证据；`na` 要有理由；`unverified` 说明未做原因和下一步；`blocked` 说明阻塞。
- 原型交付时说明已验证页面与状态、未验证范围、已批准范围、未决问题和归档路径。
- 静态说明或高保真图即使已批准，也不替代实现阶段的业务、安全、可访问性与运行验收。
