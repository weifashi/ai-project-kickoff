# 架构、数据与安全：让方案可实现、可验证

用于 G3 方案收敛，以及实现中出现的新边界、新数据或高代价技术决策。
只覆盖当前切片及已知演进约束，不为尚不存在的流量、组织规模预建平台。
资料归档与默认路径以 [documentation-and-operations.md](documentation-and-operations.md) 为唯一详细定义。
本文件中的路径是引用，不另建一套目录规范。

## 1. 先把架构输入补齐

开始设计前，从已批准的范围、用户流程和约束提取下列输入：

| 输入 | 必须明确 | 不明确时的处理 |
| --- | --- | --- |
| 关键任务 | 谁在什么场景完成什么结果 | 返回需求，不用组件名代替任务 |
| 负载形态 | 活跃量、峰值、载荷、批量、增长假设 | 先记录范围与来源，必要时测量 |
| 运行环境 | Web、原生、离线、受管设备、部署地点 | 未知环境不承诺兼容 |
| 数据边界 | 数据主体、所有者、租户、驻留要求 | 涉敏边界未定时不接真实数据 |
| 外部约束 | 身份、支付、企业集成、分发、已有系统 | 查实际契约和授权，不凭记忆补齐 |
| 团队能力 | 维护人、值班能力、预算、交付期限 | 方案必须能由实际团队运营 |

区分事实、用户决定、待验证假设；每项记录来源、日期和负责人。
已存在项目先画现状，再标本次差异；不要把目标架构当作已经落地。

## 2. NFR 必须能测，但不能替用户编 SLA

每个重要非功能需求使用下列记录结构：

```text
NFR-ID | 业务原因 | 指标与口径 | 候选目标 | 来源/批准人
       | 测量环境/负载/分位数 | 验证办法 | 当前结果 | 未知项
```

- 响应时间写明从哪里开始、到哪里结束，以及冷启动、网络和样本窗口。
- 吞吐写明请求或业务单位、峰值持续时间、数据规模与失败判定。
- 可用性写明服务窗口、成功定义、外部依赖与观测方法。
- 恢复写明可容忍数据损失、恢复时间、谁批准、演练方式。
- 原生端补充启动、内存、耗电、离线、最低系统与硬件约束。
- 可访问性、隐私、成本、可维护性按真实用户和风险选择指标。
- 用户或合同已有目标，引用原文与来源；项目历史基线也可作为输入。
- 没有来源的数值只能是待批准假设，不写成既有 SLA 或对外承诺。
- 未知规模先做有界基线测量；不要默认套用“高可用”或固定毫秒数。
- 指标冲突时明确优先级与取舍；便宜、低延迟、强一致不能口头全部保证。

## 3. 用同一组图说清边界

按决策需要画系统上下文图和 C4 容器图；复杂模块再补组件或时序图。
C4 的 container 是可运行应用或数据存储边界，**不等于 Docker 容器**。
图必须有名称、图例、方向、边界和当前/计划标记，避免仅画品牌 Logo。

```text
[用户/操作员] --操作--> [客户端]
                          |
                     身份 + 请求
                          v
                 +---本系统信任边界---+
                 | API --> 业务模块   |
                 |          |         |
                 |      数据访问层 -->[存储]
                 +----------|---------+
                            | 外发数据/副作用
                            v
                        [外部服务]
```

上图只是占位结构；按项目替换，不能暗示必须有 API、云端或数据库。
每条关键连线说明：数据类别、协议或调用方式、身份来源、超时和失败后果。
离线应用、命令行、插件、浏览器扩展应画出各自真实的进程和权限边界。
部署视图另外说明环境、区域、网络、配置注入、持久卷及升级单元。
运行拓扑与逻辑容器图分开；一张图不同时假装解释所有细节。

参考：[C4 图层与容器定义](https://c4model.com/diagrams/container)。

## 4. 模块与数据流以业务不变量为中心

为关键模块列出职责、输入输出、拥有的数据、不负责什么及可替换边界。
把规则放在可信业务层；页面校验用于体验，不能代替服务端或可信进程校验。
核心流程至少画一条成功路径和一条失败/取消/恢复路径。
明确跨模块事务、跨进程调用、最终一致窗口和用户可见状态。
涉及跨系统写入时，说明先后顺序、部分成功、补偿能力与人工处理入口。
不可补偿操作不得用“失败就回滚”一句话掩盖。
现有业务规则变更单独列“原规则 → 新规则 → 原因 → 受影响入口”。

## 5. 数据契约先于持久化实现

核心实体、API 载荷和事件至少记录下列内容：

| 维度 | 要回答的问题 |
| --- | --- |
| 字段 | 类型、必填、默认、范围、格式、空值语义、敏感等级是什么？ |
| 标识 | 由谁生成、是否稳定、可否外显、唯一性在哪个范围保证？ |
| 关联 | 基数、删除行为、跨租户关系、引用失效如何处理？ |
| 生命周期 | 创建、变更、归档、删除、备份保留由谁触发？ |
| 兼容 | 新旧客户端、旧事件与历史记录如何共存？ |
| 变更 | 回填、迁移、重跑、失败恢复及授权边界是什么？ |

金额明确币种、精度、舍入、税费顺序和记账口径，不用二进制浮点隐式算钱。
时间区分事件时刻、当地业务日期与时区；明确夏令时、跨日和展示规则。
状态机列出允许转换、触发主体、前置条件、重复事件和终止状态。
并发更新说明冲突策略：版本比较、事务、锁或唯一约束，按真实冲突选择。
幂等说明键的作用域、有效期、相同键不同载荷、结果复用及失败重试规则。
不能把客户端禁用按钮当作重复扣款、重复提交或并发覆盖的保证。
数据库约束、业务校验与错误契约要一致；未采用数据库时说明等价保障。
索引和分页按访问路径与数据量选择；不要为每个字段预建索引。

## 6. 身份、权限与多租户必须在可信边界强制

建立“主体 × 动作 × 资源 × 条件”权限表，覆盖读取、导出、批量和管理操作。
默认拒绝未明确允许的访问；鉴权失败不泄露资源是否存在等非必要信息。
角色不是唯一条件：资源归属、租户、状态、委托与字段可见性都要核实。
tenant 标识来自受信身份上下文并验证成员关系，不能直接信任客户端传值。
每次资源访问都验证归属；列表、搜索、缓存、对象存储和后台任务同样适用。
数据库行级策略可作为纵深防御，是否采用由存储能力和项目边界决定。
跨租户管理能力单列审批、审计和测试，不用“管理员”一词跳过边界。
原生本地应用按操作系统能力、应用沙箱、文件权限与用户授权设计。
MCP、CLI 或 agent 工具能调用某操作，不代表用户授权了该操作。
工具配置不是应用权限边界；仍需验证真实身份、环境与资源范围。
开发授权不默认包含生产写权限、迁移、部署、付款或外部消息发送。

## 7. 外部依赖与异步能力按需要引入

依赖表记录服务所有者、契约版本、凭据范围、配额、成本、故障模式和替代方案。
区分只读请求与有副作用操作；超时不等于后者没有执行。
结果不明先通过业务 ID、幂等键、状态查询或审计记录核对，不能盲目重试。
无可靠状态查询时，标成待人工核实并阻止可能重复的不可逆动作。
重试只用于确认可重试的错误，明确上限、退避、取消和终止条件。
Webhook 明确签名验证、防重放、重复/乱序、延迟和死信处理。
缓存仅在测量或约束支持时采用，写清真源、隔离键、失效、TTL 与陈旧容忍。
队列仅在真实异步/削峰/解耦需求下采用，写清投递语义、幂等、积压与恢复。
不要默认引入 Redis、消息队列、微服务或 Kubernetes。

## 8. ADR 记录难以逆转的取舍

影响跨模块契约、数据安全、运行成本或迁移成本的决定进入 ADR。
使用 [architecture-decision.md](../assets/templates/architecture-decision.md)，不为每个局部实现写 ADR。
一条 ADR 至少包含：背景、约束、备选、选择、代价、验证、退出和负责人。
备选包含现有方案或不做；比较依据应来自本项目而非框架流行程度。
代价包括许可、锁定、运维、人力、迁移、数据可携带性及失败模式。
退出计划写明触发条件、替换边界、数据导出或回迁路径和不可逆部分。
实验结论可以推翻草案；已批准决定被替换时保留历史并指向后继 ADR。
参考：[ADR 的背景、决定与后果](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。

## 9. 安全与隐私沿数据生命周期检查

为采集、传输、使用、共享、存储、导出、删除和备份各阶段指定控制措施。
只收集完成任务所需数据，明确目的、告知/同意要求、保留期和删除责任人。
删除要求同时考虑索引、缓存、分析副本和备份的实际可删除性与到期清理。
日志、截图、测试夹具和 AI 上下文不得无意保留令牌、个人内容或生产数据。
以合成或脱敏数据验证；真实数据的使用范围与依据必须单独确认。
加密方案明确传输、静态数据、密钥托管、轮换和恢复；不自制密码协议。
secret 通过受控配置或凭据服务注入，不入仓库、不写报告、不嵌入前端包。
区分开发、测试与生产凭据；最小范围、可撤销、可轮换，并考虑泄漏后的处理。
构建依赖、安装脚本、CI 权限、制品来源和发布签名纳入供应链检查。
使用锁文件或等价可复现机制，审查关键依赖的维护、漏洞与许可证兼容性。
许可证未知不能自动解释为可商用；不凭“开源”替代许可核对。

## 10. 威胁模型与平台安全标准裁剪

围绕资产、入口、主体、数据流和信任边界找滥用场景，按影响与可利用性排序。
至少评估未授权读取/写入、越权、数据外泄、伪造、资源耗尽与恢复失败。
为高风险项绑定控制措施、验证用例、剩余风险、接受人和复核条件。
Web/API 可选用 OWASP ASVS 的适用要求并记录版本、范围和未适用理由。
原生/移动端按对应平台风险和标准选项，不把 Web 控制项机械当作全平台验收。
涉及本机权限时检查沙箱、签名、分发、敏感授权与更新渠道；不得自动绕过授权。
需求超出团队判断能力时提出专业评审，不把清单自检描述成合规认证。
参考：[OWASP 威胁建模](https://owasp.org/www-community/Threat_Modeling)、[OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)。

## 11. 仅在产品实际使用 LLM 时追加

AI 辅助开发不代表产品需要模型、向量库、RAG 或 agent。
确有模型功能时，明确模型做什么、不做什么、何时拒绝或交由人工。
建立代表性评测集，覆盖质量、安全、拒答、错误成本与关键用户群体。
定义调用预算、token/费用上限、延迟、速率限制、降级及供应商不可用处理。
提示词注入来自用户、网页、检索文档、附件和工具返回；都不能改变系统授权。
检索前后按真实身份和资源授权过滤，不能把“能搜到”当作“能展示”。
模型输出按不可信输入校验；执行代码、写数据和外发信息仍需确定性策略与授权。
记录输入输出保留、供应商数据使用、地域、训练用途及敏感数据限制。
评测失败、模型版本变化或预算超限时应有停用、回退或人工接管路径。

## 12. 风险 spike 与 G3 放行

无法用资料确认的关键假设，安排有时限、有预算、可丢弃的 spike。
写明问题、最小实验、成功/失败阈值、证据和下一决策；不偷换成完整实现。
实验不得默认访问生产、调用收费服务或发送真实敏感数据。
G3 检查架构是否能覆盖关键体验、数据不变量、权限和可执行验证路径。
高风险未知影响正确性或权限边界时标 `blocked`；证据尚缺但可补测标 `unverified`。
门状态只用 `pass / na / unverified / blocked`；`pass` 附证据，`na` 附不适用理由。
产物另记 `draft / approved / implemented / superseded`，批准方案不等于实现已通过。
G3 通过后才将已收敛方案交给 G4 真实切片；范围变化时重开受影响决定和门项。
