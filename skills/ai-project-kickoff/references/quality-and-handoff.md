# 质量、放行与 AI 交接：证据贯穿到最终制品

用于规划验证、拆分 AI 任务、审查真实切片，以及 G0–G6 的放行与交接。
检查深度按 [平台与三档裁剪](platforms.md) 决定：默认标准，风险叠加取最高档；交付目标另记，不照搬所有项目的测试清单。
默认资料位置只由 [documentation-and-operations.md](documentation-and-operations.md) 详细定义。
下述 `docs/testing`、`docs/security`、`docs/ai/handoff.md` 是引用，不另立目录规则。

## 1. 用需求 ID 连通证据，而不是堆文档

每个关键需求、约束和被改变的原有规则都要能追到最终结果。
可复用现有 issue/测试系统；不强制为同一事实复制多份台账。
最小追溯链如下，缺一环就明确缺口和影响：

```text
REQ/NFR-ID
    |
    +--> 用户流程 / 原型 / 页面状态
    +--> API / 事件 / 数据契约
    +--> 业务不变量 / 权限 / 状态转换
    +--> 自动化测试 / 人工验收步骤
    +--> 源码基线 / 构建制品 / 签名或哈希
    +--> 发布验证 / 观测 / 回滚或恢复
```

一项需求可对应多条测试；一条测试也可覆盖多个相关需求，但不要靠名称猜覆盖。
外观相同不代表规则相同：尤其检查金额、租户、时区、并发和重复提交。
已有项目列出受影响旧规则与兼容期，新增功能不能默默覆盖旧行为。
用户明确不做的项也进入范围记录，避免后续代理补成“理所当然”。

## 2. 验收条件写成可观察结果

用“前置状态 → 操作或事件 → 可观察结果 → 禁止发生的副作用”描述关键规则。
覆盖成功、失败、取消、重试、无权限、空数据及边界值；按风险裁剪。
等待中的异步结果要有完成条件和观察位置，不能只写“最终成功”。
UI 验收写“页面 → 操作 → 结果”，标出按钮禁用、进度、错误与恢复入口。
接口验收同时检查响应和持久化/事件等副作用，不能只看 HTTP 成功码。
NFR 记录测量口径、环境和批准来源；目标未确认不能写成已达 SLA。
不可自动化的项仍要有执行步骤、环境、实际结果与证据位置。

## 3. 按风险规划测试层次

| 层次 | 优先覆盖 | 不能替代什么 |
| --- | --- | --- |
| 单元/属性测试 | 计算、不变量、状态机、解析和边界 | 外部契约、真实平台行为 |
| 组件/集成测试 | 数据访问、模块协作、真实约束 | 完整用户路径与部署配置 |
| 契约测试 | 请求响应、事件、版本与兼容 | 供应商线上健康或权限配置 |
| E2E | 关键任务、权限、持久化和恢复 | 全部内部规则的低成本覆盖 |
| 真机/目标环境 | 系统授权、输入法、设备能力、安装更新 | 所有设备和用户环境 |
| 运维演练 | 备份恢复、回滚、告警、依赖故障 | 日常功能验收 |

在最便宜且可信的层次验证规则；关键路径再用较高层证明实际接通。
mock 明确替代了什么，至少为高风险真实边界保留契约或受控集成证据。
外部服务不可用时保留 `unverified` 与替代证据，不把 mock 通过说成服务验证通过。
测试环境与生产的差异单列，避免在正确代码上验错配置。

## 4. 实现与验证的工作顺序

实现可测试行为前先给出失败用例，确认失败原因正是缺失需求而非环境坏掉。
做最小实现使其通过，再整理结构并重跑；避免测试只复述实现细节。
修 bug 先写可重现旧故障的回归用例；保留触发条件和失败证据。
遗留代码难以直接隔离时，先建表征测试或受控复现场景，再缩小修改面。
纯文档、生成物或工具限制无法采用测试先行时说明原因与等价验证，不假装已做。
权限、金额、迁移和并发不能只靠快照或 happy path 测试。
接触未知 API、编译器或生成物时可先做必要探索，探索不替代最终源码检查。
测试数据使用合成或已授权脱敏样本，不默认读取用户历史或生产数据。

## 5. 平台专项按实际交付对象选

### Web 与 API

- 验证目标浏览器、响应式布局、导航/历史、表单、网络失败与会话状态。
- 关键 API 检查鉴权、对象归属、输入校验、分页、错误结构和兼容。
- 涉跨站、Cookie、上传或富文本时补对应风险用例；未涉及项写明不适用。
- E2E 使用受控账号与数据，明确清理和外部副作用边界。

### 原生、移动与桌面

- 在声明支持的系统/设备上验证安装、启动、升级、卸载及必要的回滚恢复。
- 检查签名、包标识、权限、后台/前台、断网、休眠唤醒及系统集成。
- 最低支持版本和旧设备选择来自用户群体与支持承诺，不任意承诺全机型。
- 系统权限、真实输入、截图能力和硬件行为需目标环境证据，合成事件不等价。
- 不自动绕过 TCC、沙箱、Gatekeeper、Keychain 或其他系统授权。

### 可访问性与国际化

- 按真实用户选择键盘、焦点、读屏、标签、对比度、缩放和动态状态检查。
- 自动扫描只能覆盖部分问题；关键流程需要相应人工或辅助技术验证。
- Web 目标等级引用适用 WCAG 要求；原生按平台能力与需求验收，不能机械套认证。
- 多语言项目检查文本溢出、字体、RTL（如适用）、日期、数字和时区。
- 参考：[WCAG 2.2 快速参考](https://www.w3.org/WAI/WCAG22/quickref/)。

## 6. 最终源码、制品与运行证据分层

最终代码变化后重跑受影响检查，记录对应提交或工作树差异摘要。
运行中、超时、被截断或进程退出未知均不算通过；先取得完成状态。
验证记录至少含时间、命令/操作、环境、基线、退出结果和证据路径。
代理的“我测过了”不是证据；集成人需查看实际输出或可复核制品。
旧提交检查不能证明新源码；中间制品检查不能证明最终发布包。
失败后先定位原因；仅对明确瞬态且安全的失败有界重试，不能刷绿掩盖问题。
区分源码检查、编译、测试、打包、签名、安装、启动与实际任务验收。
哈希与签名证明身份/完整性，不单独证明业务正确或安全。
声明“已验证”时同时说清环境、覆盖范围与未覆盖边界。
文档-only 变更检查链接、路径、示例与规则一致性，不运行无关业务构建。

## 7. 安全、隐私与成本纳入放行

按威胁模型把高风险控制对应到可执行用例，尤其检查越权、tenant 与敏感日志。
对秘密扫描、依赖/许可检查和制品来源说明工具范围与已知局限。
真实服务验证必须有权限、配额和预算；开发验收不默认允许付费调用。
生产写入、迁移、发布、外发消息或支付须有对应授权，不从实现许可推导。
外部副作用结果不明时先查状态；未核实前不得重复执行不可逆动作。
发现风险未修复时写影响、缓解、接受人、期限和复核条件，不自行接受业务风险。
产品实际使用 LLM 时增加评测集、注入/检索授权、预算和降级验证。
只是用 AI 开发时不追加模型产品组件或假装已有 LLM 风险评测需求。

## 8. AI 任务包必须可以独立验收

拆分依据是明确的输入输出和可验证边界，不是平均分文件数。
使用下列最小任务包，可在 issue 或执行计划中直接填写：

```text
TASK-ID / 目标 / 关联 REQ-ID
输入：已批准决定、基线、参考、现有实现、必要数据说明
输出：预期文件或结果；允许修改与禁止触碰的文件/模块
依赖：前置任务、共享契约、环境与权限、尚未知 API
验收：测试/检查、预期结果、证据、不可发生的副作用
约束：不在范围项、授权上限、预算/时间界限、停止条件
交付：实际差异、运行结果、未验证项、风险、下一步
```

任务包不得携带密钥或不必要个人数据；引用受控凭据入口而非明文复制。
未知契约由明确负责人先确认，不能让多个代理各自发明同一接口。
任务完成定义必须包括最终变化的检查，而不是仅交付代码文件。

## 9. 并行不等于无人负责集成

仅在工具可用且用户/适用规则允许时，考虑并行独立任务。
不同任务应有独立输入、输出和文件边界；共享修改先分工或顺序执行。
不为“多代理”本身拆碎紧耦合的事务、状态机或同一文件修改。
指定一个集成负责人和一个审查责任人（review owner），可由同一人承担并说明。
各代理报告基线、变更与证据；集成人核对真实差异、接口、规则和遗漏。
先审是否满足需求与权限，再审正确性、维护性、性能和安全影响。
代理审查意见同样要核实，不能因“另一模型同意”就直接接受。
集成冲突解决后重跑受影响检查，不能沿用合并前各自的绿灯。
可提交、推送或部署与否由授权决定，任务完成不自动包含这些操作。

## 10. G0–G6 使用一套门与两类状态

G0–G6 的定义只维护在 [主入口](../SKILL.md)；具体阶段证据见 [生命周期](lifecycle.md)。
门与产物的当前记录放在 [最小状态索引](documentation-and-operations.md#13-最小状态索引)，不在本篇重建门表。

门状态只使用 `pass / na / unverified / blocked`，不额外发明“基本通过”。
`pass`：该门适用条件已满足，附可复核证据和基线。
`na`：明确不适用并写理由；不能用来藏没有时间做的测试。
`unverified`：证据缺失或环境不支持，列影响、负责人、补证方式和是否影响后续。
`blocked`：存在无法继续的必要依赖、授权或明确风险，写解除条件。
当前门未满足不宣称全项目完成；可独立进行的无风险准备工作不必一并停下。
高风险项未验证时不得以普通备注绕过放行，交由明确决策者处理。
产物状态另列 `draft / approved / implemented / superseded`，不可代替门状态。
例如 ADR 为 `approved` 仅表示方案批准；G4 仍可能是 `unverified`。
范围、依赖或最终源码变化时重开受影响门项，保留历史证据与失效原因。
放行表可复用 [startup-readiness.md](../assets/templates/startup-readiness.md)。

## 11. 交接必须支持下一位继续工作

交接写入项目约定入口；默认引用 `docs/ai/handoff.md`，不散落多个“最新”文档。
使用 [ai-handoff.md](../assets/templates/ai-handoff.md)，只保留接手需要的事实。
记录当前目标、范围、仓库/分支/工作树、重要文件、决定与理由。
记录当前 G0–G6 状态及证据，不把历史版本验收当作当前证明。
列出已完成、进行中、未验证、阻塞和放弃项；说明下一步的前置条件。
保留已执行有副作用操作的 ID、结果和核对入口，不记录秘密或多余个人数据。
给出环境启动、检查命令、复现步骤和有效文档链接，核实路径实际存在。
部署、迁移、回滚等 runbook 引用 [operations-runbook.md](../assets/templates/operations-runbook.md)。
没有权限或环境不可达时写清限制；不要要求接手者盲目重放上次命令。

## 12. 最终汇报与交付判定

用大白话先说“做了什么、实际验证了什么、还缺什么、影响谁”。
方案/报告必须走 [html-mockup](../../ai-project-kickoff-html-mockup/SKILL.md)：无 UI 用契约/流程 HTML；有实际 diff 才做阶段 B 变更报告。
有 UI 或业务规则改动时补“页面 → 操作 → 结果”、字段与旧规则变化；规则/字段以权威源码为准，不另造 schema。
列出制品位置、使用入口、备份/回滚路径（适用时）和维护责任人。
不存在的部署、未运行测试、尚未批准的决定不能写成完成结果。
用户可选择的后续动作只提供当前可执行且权限明确的选项。
G6 是交付与运营就绪判定，不是默认执行发布或安装的授权。
项目可以按约定交付源码、草案或试验结论；明确交付类型，不冒充上线完成。
源码和笔记的当前版本、验证日期与同步落后状态按 [同步与版本](sync-and-versioning.md) 回读留证，远程同步不等于已安装。
